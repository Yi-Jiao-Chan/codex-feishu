## 配置与服务管理

- `setup --input ABS --plan --json` 严格校验一期输入，实际读取所选二进制能力和现有 daemon。计划只引用受限密钥文件，不打印正文；规范化目录，沿用既有 host_id / 数据库路径，展示有效通知规则和单列的明确规则差异。
- plan_id 绑定输入、测试授权、二进制、密钥、实际环境和现有配置。预览不创建正式目录、写配置、迁移数据库、启动服务或调用飞书写接口。
- apply 内核已有部署锁、0600 备份、prepared / applied 日志、原子替换与中断后的核验。重复同一有效计划为 no-op；实际运行实例持有应用锁或数据库锁时拒绝改变配置。开发版由发布门槛拒绝正式应用。已有规则更新尚未接入事务，相关计划明确 pending，不能先部分写入配置。
- `service install / start / stop / uninstall` 接入只管理固定 `codex-feishu.service` 的用户服务管理器。检查托管身份和物理配置路径，拒绝接管其他部署、手写 unit 或 drop-in；重复操作读取实际状态。安装启用自启动而不自行启动，更新活动 unit 明确返回 restart pending。卸载保留配置、密钥与数据库。
- unit 使用绝对路径，按 systemd 参数规则处理空格、引号、反斜杠、美元和百分号；禁用 ExecStart 环境变量展开。失败时保留备份或恢复旧 unit，未能证明结果时不宣称成功。install / start 同样保留发布门槛。
- `status` 当前仅为只读快照：用户服务和注销常驻条件、现有 daemon、绑定 / 收据 / 出站 / 待处理请求计数。SQLite 使用 mode=ro 和 query_only，不创建文件、不迁移旧库、不读取正文到诊断。实时控制通道未实现，连接状态 unknown、检查 pending、退出码 5。

## 待处理提醒

schema 9 新增审批 / 问答的路由日志、首次提醒资格和冻结投递记录。App 继续负责处理请求；桥既不回答，也不存储审批命令、问题和答案。原生代际先清除未核验的 pending 状态，真实请求与完整历史重读后再启用提醒。已 resolved 或终止轮不发送旧提醒。

每个新请求至多一张固定提醒卡，引用该轮已确认的人类输入；没有可验证 parent 不发送。资格与发送前分别核验通知策略和群成员，off / snooze / quiet 或成员不可证明时终止该提醒。未知结果冻结，不重发新 @，也不在休息时间结束后补提醒。

原生 0.162.0 请求没有发生时间，重连重放与旧轮中的新请求存在歧义。当前只对本代际新生主会话首轮、或 startedAt 严格晚于首次历史核验秒的后续轮授予新提醒资格。旧执行轮和同秒歧义仍可显示回 App 提示，但不新 @。这属于明确的开发边界，不代表全部 needs_user 场景已完成。
