# 13 飞书内审批与用户问答：扩展方案

日期：2026-10-14。状态：**命令审批（允许本次）与同步问答已通过真实双端验收，并在本机常用候选服务启用**。实现了原生回复、独立请求卡、表单回调、动作收据、恢复与按类型开关。其余类型保留待验收状态；不能把本地测试或合成卡预览当作 App/飞书实际审批验收。

目标：App 发起的任务需要人类决定时，可以在飞书卡片上完成操作，原任务继续执行，App 与飞书同步结束等待。继续复用原共享 daemon、线程、权限策略、原生队列和现有长连接。

## 1. 结论与证据

核心功能有现成协议基础，可以作为现有桥的增量扩展。[OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)说明了命令、文件、权限审批、原生问答和 `serverRequest/resolved` 生命周期。[飞书研究记录](../research/feishu-interactive-requests-2026-10-14.md)核实了卡片按钮、表单和长连接回调。

本机只读核验：`codex app-server daemon version` 报告 CLI / App Server 均为 **0.162.1**；执行 `codex app-server generate-json-schema --experimental --out <临时目录>` 导出 447 份 schema，没有启动新的服务。逐项读取审批/问答 Params、Response、`ServerRequestResolvedNotification`、`ThreadReadResponse` 和 `ClientRequest`，确认了下表字段。临时协议文件不作为用户数据提交。

`RequestTracker` 继续维护等待和原始提醒证据；`Client.RespondServerRequest` 新增带 generation、原始 ID 和完整结果校验的回复入口。`internal/interactions` 将请求持久化为独立操作卡，复用线程 actor、既有飞书接收器与 outbox。未启用类型保留回 App 提示。

当前证据：0.162.1 隔离双客户端原生问答已通过桥端 `Parse → Build → Respond`，另一客户端收到同一 `resolved`，原轮继续完成，第二次回答被拒绝。命令探针在继承的 `permissionRequest` hook 阶段未到达原生审批，保持 pending，不关闭 hooks 绕过。三种合成卡（命令、问答、权限）均已被飞书 API 接受并读回；字段 `input_type` 已经真实发送核验。用户已确认第三版紧凑问答与权限同行按钮布局。

2026-10-14 的真实 App / 飞书两题问答已通过：用户在自动创建的测试群选择两项并提交，App 解除原生等待，最终回复只同步一次；用户确认“没问题”。私有数据库记录同一请求 `resolved`、一次 `submitted` 动作和一次已确认最终投递。该证据覆盖真实表单回调与 App 等待界面，不覆盖其他审批类型、手机输入或异步问题组件。实际题文、答案、请求 ID 和群 ID 仅保留在私有证据目录。

随后真实 App 默认权限下的命令审批也通过：飞书允许后，原 App 任务继续，隔离目标文件内容匹配测试标记，审批动作 `submitted`、请求 `resolved`、最终投递各一次。App 先回答的第二次原生问答也正常闭合，飞书没有创建回应尝试。用户确认执行正常，并指出已处理卡没有显示选中答案、App 问题控件没有回显外部选择。

已据此实现紧凑问答收据：问题和实际回答在正文，完整选项默认折叠；未知答案不猜测推荐项。只读适配器从 daemon 返回的原生 rollout 路径取得实际工具输出，核对 session、turn、call ID 和冻结的问题，读回两组真实问答结果后原位更新原卡，两张卡 API 读回通过。

V3 新会话复测已通过：第一题在飞书提交选项及补充文字，第二题在 App 回答，用户确认“没问题了”。同一轮的两份原生请求均 `resolved`，飞书只产生一次提交尝试；两份实际工具输出均持久化，两张已完成卡的 API 读回包含问题、实际答案和折叠详情。校验采用实际选择，不假设用户选择推荐项或测试指引中的某一项。题文、补充文字、请求 ID 和群 ID 继续仅存私有证据。

本机常用候选已启用 `enabled_types = ["command", "question"]`，运行代码身份为 `d43151a776a157492ad88a3c2b82a21bca576502`。停桥后创建一致备份，先在副本核验 23→25 迁移，再升级运行库；全部 42 个既有表的列、行数和行值摘要一致。新服务的二进制身份、两个连接及 16 个可用绑定均已核验。整体 doctor/status 仍为 pending：另有 4 个已归档绑定，以及切换前已存在的 2 条 unknown 投递；不强行解除归档或重发未知结果。该记录是按类型开启扩展的证据，完整一期发布与其余类型 UI 验收继续保留原门槛。

## 2. 用户体验

### 审批卡

沿用已经确认的正文优先样式：无彩色标题，状态和来源用小字，原因和真实影响用正常字号，8px 组件间距。提醒用户放在首段开头，与正文同行；审批请求本身按 `needs_user` 提醒规则发送一次，免打扰只控制 @，始终展示可操作卡片。

合成示意，方括号表示控件：

````text
允许执行这条命令？                              加粗正常字号
等待你确认                                      小字状态

@你 需要执行下面的操作，以完成本轮验证。

```bash （原生代码块）
go test ./internal/...
```
工作目录：/workspace/project                     小字

▸ 完整命令与权限范围                            单行折叠

[允许本次]  [拒绝]  [停止本轮]

│ 审批请求 · Codex                              小字来源
````

- 原因来自请求的 `reason`；没有原因时展示原生操作类型、命令/路径，不编造目的，不额外调用模型改写。
- 权限卡的多选下方同一行排列 **允许 / 允许本轮全部 / 拒绝**。“允许”提交所选子集；另外两个按钮仍携带表单当前值，但后端仅在名称、类型和值通过校验后忽略选择，按显式决定授予原请求范围或拒绝。
- 问答采用 compact 宽度；题号/短标题为 notation，问题加粗正常字号，选项说明小字。输入框 `input_type=multiline_text`、`rows=1`，桌面随输入增高，手机保留多行输入能力；提交按钮自适应内容宽度。控件布局仍需客户端实测。
- 命令卡显示工作目录、真实命令及追加权限。短命令可直接展示代码块；长命令保持完整可展开，审批对象始终是服务端原始值。
- 文件卡通过 `itemId` 关联对应 `fileChange.changes`，逐文件展示增删改、路径和 diff；只有文件清单而没有 diff 时明确说明。缺少足够操作详情的请求暂不提供“允许”，仍可拒绝或到 App 查看。
- 网络卡突出 host 和 protocol，不用无意义的 shell 预览替代网络授权范围。0.162.1 的该结构没有独立 port 字段，不凭文档概览拼造端口。
- 权限卡列出请求的文件系统读/写范围及网络权限；只返回原请求的子集，默认作用域 `turn`。不能把对某条命令的授权改造成整个会话 Full Access。
- 默认两枚小按钮“允许本次 / 拒绝”；更多决定按请求提供的可用集合呈现。若“停止本轮”可用，明确对应原生 `cancel`；“拒绝”对应 `decline`，允许 Agent 继续选择其他方案。
- `availableDecisions` 非空时严格采用原列表；缺省时仅使用已验证版本适配器支持的基础决定。会话缓存授权必须准确描述匹配范围；持久命令/网络规则待专门核验后提供，不能叫“永久允许所有操作”。
- 普通允许/拒绝直接提交，不增加重复确认弹窗。选择较长授权范围时，在控件旁明确说明范围。

### 问答卡

```text
等待你回答                                      小字状态

@你 这次采用哪种处理方式？

A · 保留现有布局，只修复引用换行
B · 同时调整正文与执行过程布局

[选择一个答案 ▾]
[补充说明或自行填写……]

[提交回答]

│ 用户问答 · Codex                              小字来源
```

- 一个原生同步请求对应一张卡，多个问题按原顺序展示，一次提交整份回答。
- 飞书公开组件没有文字 radio 组，使用 `select_static`。原协议明确支持多选的其他表单才使用 `multi_select_static`，不能仅因 `answers` 是数组就把普通单选问题改成多选。
- 完整选项说明放在下拉框前；选项值使用服务器内部映射，提交时恢复原 label，不能把序号或翻译后的 label 当作答案。
- 自由回答使用多行 `input`；选项、补充文本及 `isOther` 的组合按准确版本适配，保留用户填写的正文，不把“其他”占位词当答案。没有选项时直接文本输入。
- 无自动提交；选项改变只是草稿。所有题目校验通过后才领取动作，某题缺失或非法时保留整份请求，不提交部分答案。
- 请求处理后的卡片展示紧凑收据：小字“已回答”，问题和实际回答各一段，原题标题、选项和说明默认折叠在“问题详情”。只有核实原生工具输出才显示“已回答”；仅有飞书提交意图时标为“已提交的回答”，没有实际答案时显示“请求已处理 · 暂未取得回答”。
- 等待填写时**不随执行过程 tick PATCH 问答卡**；请求被领取、作废或处理完毕时才更新。form 放在顶层，与折叠详情同级，不塞进过程卡的折叠面板。
- 飞书输入组件每项上限 1,000 字符，不静默截断。初版遇到长回答提供明确提示；若要完全在飞书完成更长输入，后续增加“长回答”草稿入口：仅接收授权人的引用回复，按请求/题目绑定，收齐后仍需点击提交。普通群消息继续走原有队列，不能被误收为答案。
- 任一题 `isSecret=true` 时，整份原生请求不在公共卡片收集答案，避免提交残缺回答；密码遮罩不等于保密。登录或身份验证沿用其原界面。

### 与过程卡的关系

每个待处理请求一张操作卡，引用本轮起始人类消息；App 输入引用已镜像的人类消息，飞书输入直接引用原消息。现有过程卡仅显示“等待审批 / 等待回答 · N 项”，继续保留可展开执行历史。完成后操作卡保留为紧凑收据，最终 AI 回复仍单独发送。

普通问题卡、异步问题消息的镜像要合并为一个展示入口，避免又发一张包含同样问题的“最终回复”卡。同步答案走原生工具响应，不再伪造一条普通用户消息进入队列；App 的问答展示以原生结果为准。

## 3. 原生响应与异步问答必须分开

### 同步请求与审批

原生服务端请求的 JSON-RPC `id` 才是回复标识，保留 string / integer 的真实类型；`itemId`、`turnId`、`approvalId` 都不能代替。一个工具 item 可能产生多个审批 callback，不能按 item 去重。

正确回复是发送对应的 **JSON-RPC result**，不是再次调用审批 method，也不是 `queue/add`：

```json
{"id":"synthetic-native-request","result":{"decision":"accept"}}
```

```json
{"id":123,"result":{"answers":{"layout":{"answers":["A · 保留现有布局","补充说明"]}}}}
```

两者仅为合成示例；真实 question ID、答案组合、决定及类型均来自服务端记录。权限请求使用 `{permissions: <获准子集>, scope: "turn"}`；不套用命令审批的 `decision`。

普通飞书聊天仍默认排队；审批和同步问答的显式卡片提交直接回复正在等待的 callback，不排到该轮之后，否则会造成等待无法解除。点击卡片已是明确的本次操作。

`isBlocking=false` 的 `item/tool/requestUserInput` 仍是服务端请求，需要对应响应；不能仅按这个布尔值归类为下面的异步问答。`autoResolutionMs` 不作为桥自动提交空答案的依据，其他客户端先清理请求时依 resolved 作废卡片。

### 异步问答

本机协议中，`agentMessage` 可包含 `delivery:"async"` 和 `questions:[{title,options}]`。这一类没有上述 pending callback，也没有公开的专用“回答异步问题”客户端 method。官方固定版本实现会直接返回 `accepted:true` 并让 Agent 继续工作，来源及边界见[异步问答实现研究](../research/approval-routing-0.162.0.md)。

- 扩展 `codexclient.Item` 读取 delivery/questions，按 thread + 原消息 item ID + 题号建立问答身份。
- 卡片提交生成包含原问题与答案对应关系的普通输入，复用现有可靠的原生队列链路；执行中默认排队，现有追加引导入口继续可用。
- 卡片准确显示“回答已排队 / 已进入会话”，不写“原生审批已完成”，也不把一条异步问题误认为最终任务结果。
- 首先在隔离会话中确认 App 所用答复格式与问题组件的关联。如果公开输入只能回显文字，应明确保留“结构化文字回显”的限制，不能声称 App 选择控件已变成已答。该缺口不影响审批与同步问答的原生回应路线。

## 4. 双端一致性与恢复

原生请求的处理状态与本地提交收据分开保存，避免把“连接写成功”“请求已清除”“工具执行成功”混成同一结果。

| 事实 | 卡片行为 |
| --- | --- |
| 当前连接收到 pending 请求 | 展示有效控件 |
| 飞书动作已落盘领取 | 同卡显示“已收到，正在提交”；关闭本地重复领取 |
| 响应已写到连接，仍无终态事件 | 显示“已提交，等待状态确认” |
| 收到 `serverRequest/resolved` | 去掉控件，显示“请求已处理”；与原提交收据分开呈现 |
| 相关工具明确开始/完成 | 显示该实际执行状态；批准不等于执行成功 |
| App 已处理或本轮已结束，再点击旧卡 | 提示请求已结束，不发响应 |
| 发送中断或响应归属不明 | 显示“正在核验”，不盲目重发决定或答案 |
| 桥断线 | 禁用提交；重新订阅原线程等待原生 replay |

`serverRequest/resolved` 在 0.162.1 只有 `threadId/requestId`，没有决定、操作者或确认桥的响应获胜的字段。**不能仅凭 resolved 写“已在 App 回答”或“飞书批准成功”。** 两端同时提交时，服务端首个响应消费共享 callback，错误格式也可能让请求结束，所以发送前必须完整校验 DTO。本地数据库仅保证飞书动作单次领取，不能锁住 App。[官方生命周期](https://learn.chatgpt.com/docs/app-server)、[callback 行为研究](../research/approval-routing-0.162.0.md)

建议收据文案为“已提交：允许本次；请求已处理”或“请求已结束”，有后续 item 状态再补充“执行中 / 已完成 / 已拒绝”。除非协议提供了可验证证据，不宣称某个客户端赢得竞态。

**实际回答与 App 控件回显：**0.162.1 的 typed `thread/read` / `thread/items/list` 没有 materialize 原生问答的 function output，标准 resolved 通知也不带选项。当前通过原生 rollout 的唯一 `request_user_input` call/output 读回实际答案；`interaction_answers` 单独保存这份结果，不混入提交尝试，断线投影仍保留已核实收据。读取只接受服务用户的 `CODEX_HOME/sessions` 或 `archived_sessions`（缺省为 `~/.codex`）、daemon 提供的绝对路径、所属用户的普通文件；逐级拒绝 symlink、目录逃逸和外部可写文件。有总量/行大小限制；目标 turn 内的重写、中断后迟到输出、重复 call、部分答案、身份歧义均不能提供实际答案。较早的历史压缩之后必须有明确的新 turn 边界。

该适配器补足飞书收据，不会改变 App 的原问答组件。真实 App 已能解除等待、任务取得答案，但外部选项的勾选态没有通过已核验的标准接口回显。`thread/inject_items` 会改变模型可见历史，忙时进入 pending input，不能把它当作 UI-only 回显修补；本扩展不靠额外普通输入制造一次回答。这个 App 显示限制单独保留，不写成已通过。

恢复规则：

1. 请求原始 ID 和回复能力绑定当前 `connectionID/generation`。服务重启后旧连接的请求不能直接回复到新连接。
2. 持久请求身份保存 host/app/thread/turn/method、原始 ID 的类型与值、item ID、载荷指纹、卡片 ID；连接身份独立保存。重连收到原生 pending replay 并重新校验完整载荷后，才能重新绑定发送能力。
3. 可复用已发送的同一请求卡，但更新 revision/token，旧按钮失效；历史提交意图不会因为 replay 自动重发。
4. 当前公开协议没有 pending 列表或“replay 已完整结束”的保证。未看到 replay 不代表请求已经解决：没有终态证据就显示待核验，不靠固定等待几秒强判成功。
5. resolved 或轮次取消/完成清理对应等待；异步问答另按自身收据与输入消费状态处理，不能在普通轮次结束时误删仍待回答的非阻塞问题。
6. 断线与超时不自动允许、拒绝、回答或中断任务。
7. 异步问答的 App 回答只依据同一完整历史中的原始 envelope、精确 call ID/题目和先题后答的顺序闭合。完整回答显示请求已处理；部分回答、跨轮复用 ID、冲突题文/选项只禁用并保留回 App 提示。只读状态重连后不恢复按钮。
8. 异步问答没有原生 callback 仲裁。桥自身只创建一次回答收据，但 App 与飞书几乎同时发送异步回答时，原生队列可能接受两个输入；不能承诺跨端 first-wins，也不能为消除重复自动删除 App 输入。正常同步请求仍由原生 callback 仲裁。

## 4.1 配置与验收操作

默认不开启；缺省配置保留原回 App 行为。显式开关须列出已验证的类型，重复或未知类型被拒绝，例如仅开启同步问答：

```toml
[interactions]
enabled = true
enabled_types = ["question"]
```

可列出 `command`、`file`、`network`、`permissions`、`question`、`async_question`。此清单表示启用范围，**不是这些类型均已通过真实验收**。`version --json` 报告代码能力和 `feishu_interaction_ui_verified=false`；`doctor` 只读报告开关/类型，不凭连接正常宣告 UI 通过。setup 重跑保留已有配置中的选择，不自动开启新类型。

本轮类型验收记录：

| 项目 | 当前证据 | 真实双端状态 |
| --- | --- | --- |
| 同步多题问答 | 0.162.1 原生双客户端；真实 App / 飞书表单、解除等待、最终单次投递；用户确认 | pass |
| App 先处理后的旧问答卡 | 真实 App 先答后正常闭合，飞书没有新增尝试；V3 实际答案持久化、原卡读回及客户端布局确认 | pass（App 原控件的外部勾选态仍见上节限制） |
| 飞书提交后的问答收据 | V3 选项和补充文字均出现在实际工具结果及已完成卡；用户确认布局 | pass |
| 命令审批 | 真实飞书允许，App 继续，隔离目标文件正确，最终投递一次；用户确认 | pass（允许本次） |
| 文件、网络、额外权限 | DTO / 原始范围 / 子集 / 截断只读测试；权限同行按钮预览确认 | pending |
| 异步问答 | 原生历史关联、默认队列、歧义只读与恢复测试；实际 App 组件待确认 | pending |
| 本地回归 | 全包测试、修改模块 race、`go vet`、diff 与密钥扫描；实际答案优先于本地意图、重开/离线收据保留 | 自动检查通过，不能替代上列 UI 验收 |

候选验证按以下顺序，用户只需集中做最后三组：

1. 本地：完整回归、race、`go vet`、23→25 和 24→25 加法迁移保留绑定与消息收据、双击/旧卡/转发/无授权/秘密问题/预算截断/断线 unknown 等检查。普通日志不保存真实问题与回答。
2. 实际共享 daemon：在隔离线程验证原始 callback 回复，保留原 hooks；问答已通过，命令 hook 阻塞项保持 pending。不能用模型普通文本输出替代原生审批事件。
3. 卡片：先给本人发无效 token 的合成预览，核验布局、下拉、多选和输入。预览不能审批任务，生产开关仍关闭。
4. 独立候选目录/数据库验证：限制发现根目录为自有测试目录，群只加本人；新 schema 25 数据库与生产 schema 23 分开。接收器只运行一份，测试期间仅暂停飞书桥，daemon 与 App 保持。退出测试后恢复原桥，不迁移原数据库。首轮 schema 24 测试库备份后升级至 25，仅读回原生答案并更新原测试卡；不是原运行数据库的升级。
5. 用户三组：App 原生审批在飞书决定；App Plan 原生多问在飞书填写；App 先处理后旧飞书按钮失效。协议/类型实际没有触发时只记录 pending，不反复让用户重做同一无效场景。异步 App 问答组件回显单独记录，不借同步问答通过覆盖。
6. 每种类型分别通过再写入正式配置；停桥、一致备份 schema 23、安装与源码身份匹配的候选二进制、事务迁移 25，再启动桥并执行只读 doctor。绑定、队列、通知规则和原消息 ID 保留。共享 daemon 不重启。

schema 24 新增 `interaction_requests` / `interaction_attempts` 与索引，schema 25 单独新增已核实工具输出的 `interaction_answers`。迁移后旧 schema 23/24 二进制不能直接使用该数据库；回退须停桥并恢复对应的一致备份和旧配置/二进制，不修改 `user_version` 冒充降级。线上扩展开启与完整一期发布为不同验收，不提前切换 `phase1_released`。

## 5. 模块拆解

| 模块 / 文件范围 | 交付内容 | 关键验收 |
| --- | --- | --- |
| `internal/codexclient` | 准确版本的请求/回复 DTO；扩展 Item 的 command/changes/delivery/questions；受约束的 `RespondServerRequest` | 原始 ID 类型不变；连接/请求身份不符不写；普通未知请求仍不自动回应 |
| `internal/app/request_tracker.go`、`internal/interactions` | 保留等待/提醒证据；新模块保存原始请求载荷、处理 replay/resolved、关联起始输入、区分同步/异步 | 同一请求只出一张卡；多个 callback 不按 item 合并；敏感字段不公开 |
| `internal/store` | 请求、卡片 revision/token、操作人、提交尝试及三态结果；迁移兼容现有 schema | 领取先落盘；双击只一次；重启 unknown 不变成待重发；已有绑定/镜像不变 |
| `internal/interactions`（新增） | 白名单类型的校验、决定/答案组装与单次发送；复用线程 actor | 不另造执行队列；不在数据库事务或 reader 锁内等待网络/终态 |
| `internal/cards` | `InteractionView`、已处理/断线收据、纯渲染 demo JSON；字节/组件数限额含 mention/marker 预留 | 与当前字号/引用/折叠样式一致；截断卡全只读；没有默认自动提交 |
| `internal/app/receiver.go` | 新动作路由、读取 `Action.FormValue`、验证操作人及消息绑定 | 3 秒内确认；非法字段不领取；App 先答时旧卡失效 |
| `internal/sync`、通知规则 | 引用投递、按卡片顺序 PATCH、每请求首次 needs_user 提醒 | 关闭 @ 后卡片仍出现；重连不补 @；不重复镜像飞书回答 |
| `compat`、配置/doctor | 各请求类型能力清单，增加独立开关，如 `interactions.enabled` | 未验收类型无按钮；开启不修改原线程权限策略 |

沿用现有长连接 `card.action.trigger` 和 message PATCH/outbox，不另建公网回调服务。本机依赖 `oapi-sdk-go/v3 v3.12.0` 已有 `CallBackAction.FormValue map[string]interface{}`，现有 gateway 把原 SDK 事件交给 Receiver；新增字段解析须保留数组/布尔/数字的真实类型。

回调流程为：校验操作人、opaque token、revision、请求状态和真实 chat/message 绑定 → 短事务领取并保存精确决定/答案 → 3 秒内 info toast → 线程用例单次发送 → 事件驱动更新原卡。发送用例完成写入后让出执行，不阻塞负责处理 resolved 的事件流。消息更新采用已有统一 outbox；不混用 callback token 延时更新造成旧版本覆盖。[飞书回调](https://open.feishu.cn/document/feishu-cards/handle-card-callbacks)

请求卡投递与提醒资格分开：现在仅提醒用途的 `request_mentions` 不能成为“发送操作卡”的前提。操作授权使用现有 access operator 身份，@ 目标使用通知配置，二者不能互相替代。答案、命令和 diff 仅存私有运行数据库，沿用文件权限和脱敏诊断；不进 Git 或普通日志。

## 6. 实施与验收顺序

### 第一步：实际版本协议验证

只用自有隔离线程和合成输入，复用正在运行的 daemon。先建立两个订阅客户端模拟 App 与桥，验证桥能回复命令、文件、权限、同步问答；再验证首个响应、replay、旧 ID、断线及异步回答链路。不改已有线程策略，不为避开 hooks 限制关闭管理策略。遇到 host hook 未产生审批，记录观察缺口，不用 mock 通过替代真实审批。

这一阶段先回答两项关键问题：飞书端回应后 App 请求能否正常关闭；异步答复能否与 App 问题组件关联。协议模拟、静态 JSON 和官方文档均不能代替客户端确认。

### 第二步：卡片 demo 确认

产生合成的命令、文件、权限、单问题、多问题、异步问答、已处理/过期/断线样例。先看真实桌面和手机效果再定稿；卡片 demo 不持有有效审批 token，不执行任务。重点检查表单提交、逐文件 diff、长路径、字号、折叠、App 抢先处理，以及等待填写时不受过程刷新干扰。

### 第三步：实现、集中联调与开启

实现上述模块；至少通过以下病例：

1. App 发起真实审批，飞书允许/拒绝，原线程继续或改选其他方案；最终结果只出现一次。
2. App 发起单/多问题，飞书提交后等待解除，答案进入原生工具结果；普通消息仍默认排队。
3. App 先处理、飞书先处理、两端近同时处理、飞书连续点击，均无第二次执行；竞态提示符合证据。
4. 两个 native callback 共用 itemId、不同 turn、整数/字符串 request ID，均正确定位。
5. 有授权的人与非授权群成员、转发卡片、旧 token/revision，越权操作不能产生回应。
6. 写入后丢连接、收到 resolved 前桥重启、daemon 实例变化、缺少 replay，均不重发旧决定或答案。
7. 关闭 @、quiet/snooze、重连时，操作卡持续可用且不补发旧提醒。
8. 卡片 PATCH 失败不重复原生响应；原生发送失败不显示成功；resolved 后工具失败不显示任务完成。
9. 异步答案默认排队、显式引导、App 显示和输入去重分别验证。
10. 表单无答案/其他文本/超长文本、秘密字段、过期请求、手机折叠与输入布局符合本方案。

优先自动完成协议与故障病例；用户最后集中确认“飞书审批、飞书问答、App 先处理”三组关键体验。原生协议和 demo 未通过的类型维持回 App 提示；已验收类型可通过开关单独开启，不以全部未知类型阻塞普通场景。

建议本轮交付**普通审批 + 同步/异步问答卡片**。MCP 通用表单、持久授权规则和长回答草稿列为后续扩展，各自采用相同身份、收据和卡片基础。
