## 入口路由表

| 位置与输入 | 行为 |
| --- | --- |
| 机器人私聊：/new 或普通文本 | 建草稿，正文预填 |
| 已授权、未绑定入口群：@机器人 /new 或普通文本 | 建草稿，当前群可作话题目标 |
| 已绑定任务群：普通 @ 文本 | 进入现有线程，不建任务 |

命令解析必须先识别 /new，其他普通文本按位置路由。已知管理命令的拼写错误提示纠正，不把 `/notify ...` 误当新任务内容。

## 草稿与目录

draft 保存 creator、入口 message ID、任务文本、host、selected_directory、可选 project_id、follow_mode、target_workgroup、revision 和期限。草稿修改不创建远程对象；同一输入事件只生成一个草稿。任务正文最多 4000 字，超长输入明确反馈；飞书可编辑输入框最多 1000 字，较长正文完整折叠保留，提交不会截断。

用户已选择将速选、搜索与目录面板组合，并在新版原型中选定“浏览优先”。主创建卡只呈现任务、唯一已选目录、更改目录、跟进位置与最终创建；目录变更先保存任务和跟进选项，再进入同一草稿的目录视图。默认目录仍只取可核验的最近 / 常用目录，没有可靠默认时明确要求选择，不用服务进程 cwd。

目录视图顶部只有一个“当前层目录名或完整路径”输入框：显式查找名称时过滤完整当前层，输入绝对路径时只进入该目录，不自动选用。子目录下拉置于 form 外，选择后直接通过 action.option 导航；唯一主要操作是“使用当前目录”，保存后回主创建摘要。常规操作采用中号描边按钮和按内容宽度横排，主要确认采用 primary_filled。目录名与短父路径常驻，点击父路径展开完整路径与主机，表单显式 8px 间距。主卡和目录视图不重复堆叠搜索、路径输入、面包屑及多处目录确认。

最近与 Codex 项目保留为浏览视图的辅助入口；最近记录按 deployment 和 creator 隔离。项目名只查已知项目、最近和常用路径，不递归扫描整台机器。少量结果在路径旁直接使用，较多结果通过有界下拉与相邻确认操作选择。搜索、浏览和速选只修改草稿，所有非主创建视图都拒绝最终创建，避免误用旧目录。目录权限或读取错误也保留任务和原选择。

目录面板复用既有长连接回调和原卡更新，无需域名、HTTPS 或 OAuth。单层扫描仍有 4096 项上限，候选批量改为最多 100，实际返回还受完整 JSON 字节预算限制；查找在分页前覆盖整层。明确显示载入范围和总数，只在容量超限时提供继续加载，不再固定 10 项翻页。目录进入与查询不附带无关的项目目录或工作群 RPC，选择和执行前仍核验真实目录与项目。

操作持久领取后唤醒处理器；卡片以同一有序更新出口呈现正在打开、查找、保存及结果。处理中不可提交冲突操作；未知卡片写先读回，不让迟到的 busy 覆盖结果，也不盲重发。所有回调沿用实际卡片、创建者、deployment、token、revision 与期限校验。设计依据及证据边界见[重设计方案](../research/feishu-create-directory-ui-redesign-2026-10-15.md)；真实飞书手机布局和更新时延仍须单独验收。

其他目录选择卡允许在配置范围内浏览目录或输入绝对路径，所有校验发生在远程执行主机：真实路径、目录存在、可读写、允许范围、projectId 是否与目录匹配。worktree 和项目原路径沿用 07 的规范化函数。项目关系无法验证时可以无 projectId 创建，但卡片明确“独立目录”，不伪造项目归属。

mute 只阻止自动建群，用户主动创建不因此被拒绝。selected_directory 始终只有一个值。

## 新建工作树

创建卡默认使用“当前目录”；可切换到“新建工作树”，选择本地或远端基准分支。切换时保存已编辑的任务和跟进位置，分支选择随最终创建一同提交。Git 仓库须已有提交；非 Git 目录继续使用当前目录模式。分支下拉优先显示原选择、当前分支与 main/master，最多 100 项，并按完整卡片字节预算收缩；已删除的原选择不会自动换成其他分支，卡片提供仍可用的分支重新选择。

本机 0.162.1 的 `thread/start` 没有创建工作树参数。桥先创建自己的持久 Git 工作树，再向原共享 daemon 传入该工作树的实际 cwd 和经核验的原 projectId。工作树基于所选分支的**已提交内容**，以 detached HEAD 检出；原目录未提交或未跟踪的文件不会复制，环境 setup 和 `.worktreeinclude` 也不在本次实现中。这与 [Codex App 工作树](https://learn.chatgpt.com/docs/environments/git-worktrees)的自动复制和环境流程有明确区别，卡片直接说明使用已提交内容。

新工作树保存在 `<initialize.codexHome>/worktrees/<4位ID>/<仓库名>`，对齐 Codex App 的默认目录形式；Codex Home 取实际共享服务握手，不读取桥的 HOME / CODEX_HOME 作为替代。规划时跳过已有目录，创建时以原子 mkdir 领取；若被其他工作树抢占，拒绝写入。桥使用自己的私有 marker，不改 App 元数据，也不接管 App 的清理、环境 setup 或 handoff 生命周期。此前冻结的数据库同级 `worktrees/<draftID>/checkout` 保留原路径、marker 和请求参数，不移动已有会话。

用户所选目录与整个 Git 根目录都必须在 creation.allowed_roots 内；只允许 `/repo/sub` 不授予检出整个 `/repo` 的权限。允许整个仓库时，选择子目录会保留相同相对 cwd。新路径不扩大普通目录浏览权限，项目关系仍从原目录和原生 catalog 核验。

schema 29 冻结工作方式、精确 ref、commit、Git 根/common-dir 与唯一目标路径。创建工作树作为独立 attempt，在 Git 命令前落盘；不切换原分支、不创建新分支、不修改全局 Git/Codex 配置。重启后只以私有 marker、准确注册路径/common-dir、固定 commit、无初始化锁且完整干净的检出确认 unknown，缺证据不重跑 add。之后已确认的工作树允许正常修改和提交，不再要求保持初始 HEAD。群描述、原生创建/恢复与持久绑定均使用实际执行 cwd。

创建后的 Runtime 授权同样精确比较冻结的 `ExecutionDirectory()`，不拿原仓库 cwd 比较新工作树。原选择目录及整个 Git 根仍须在 creation.allowed_roots 内，私有工作树不必直接位于可浏览范围；收发前只读核验完整草稿 marker、准确注册的 checkout/common-dir 与实际 cwd/RWX。目录被移除或被其他任务复用时拒绝执行，不重建工作树、线程或群。已确认的原输入通过历史收据核对，尚未 dispatch 的普通输入沿用原收据提交。

已通过实际 Git、崩溃恢复、目录范围与 schema 28→29 保留测试；0.162.1 共享 daemon 已验证新工作树、原项目身份、首条输入及持久化后第二连接 resume。飞书新控件已通过真实平台 PATCH/GET 校验并部署候选；实际回调、创建到 App 工作树展示与客户端继续须单独验收，不据此提升完整 P2 或一期发布状态。

## 专属群与话题

默认 group：创建机器人与 owner 的任务群；卡片明确显示“新建专属群”。topic：在已授权工作群发送任务根卡，保存 root_message_id / 平台 thread ID。来自单聊时必须选工作群；没有可用群时不执行，保持草稿或切回 group。

同一群可有多个 topic binding，按原始 root/thread ID 定位。脱离已绑定话题的 @ 不猜最近会话：引导进入对应话题或建新草稿。所有回复、通知和错误都保持 topic，失效时不降级为主群。创建完成后根卡再失效，也会原子标记 binding 待修复并刷新原入口卡；重复核验不重复刷新或重新创建。

## 可恢复创建流程

```text
草稿提交（领取唯一 token / revision）
  → 校验目录、项目、成员和位置
  → 持久 create intent
  → 如选择工作树：持久记录并创建/核验同一个工作树
  → 创建目标群，或创建任务根卡
  → 保存目标平台 ID
  → thread/start(cwd, 可选 projectId, 桥自建 threadSource)
  → 保存原生 thread ID + binding
  → queue/add 首条输入（复用 input_receipt）
  → 核验首次执行 / 排队 + App 可见性
  → 更新入口创建卡与目标任务卡
```

threadSource 使用该版本支持的自建来源字符串；discovery 同时按本桥 binding / intent 排除，不能只依赖一个来源字段防重复群。初始权限采用 Codex 既有默认/所选项目策略，不启用 bypass，不复制当前 Agent 的特殊授权到新线程。

每个远程步骤都有 prepared / dispatching / confirmed / unknown 记录。重复提交返回原 intent 进度，不从头再建。群已建、线程明确创建失败时保留已有群，允许“继续创建会话”；线程已建、首条输入失败时继续该线程与原收据。

thread/start 响应丢失属于关键 unknown：本机尚未证明可通过唯一 client token 去重创建。需要先查询自建标记、目录、时间和可用元数据核验；不足以唯一定位时保持阻塞，不重复 thread/start。二期验收前若需要可靠自动恢复，应验证当前协议可用的持久创建标识；不可声称“多重条件相似”就是严格唯一。

首条输入前 rollout 可能不存在，另一个客户端 resume/read 会暂时失败。拿到 thread ID 后先在原客户端提交首条输入，等待持久化/原生事件，再验证 App；不要重新 thread/start。App 侧可见性的稳定实现是二期发布门槛。

## 验收

1. /new 与普通文本入口均有预填草稿；绑定任务群中的普通 @ 只跟进原线程。
2. group 默认值、topic 工作群选择、单聊无默认工作群的反馈正确。
3. 实际 cwd / projectId / 权限正确；主机无权访问的目录不能执行。
4. 重复 callback、群成功线程失败、线程成功输入失败、创建响应丢失均不生成第二套对象。
5. App 出现该线程，App 与飞书继续同一 thread ID；discovery 不再建群。
6. 两个话题并行及根消息撤回，内容不串话题也不落主群。
7. 当前目录/新建工作树切换保留草稿；所选分支版本和实际 cwd 正确，原目录修改保留；工作树创建中断不重复创建，半成品不启动会话。
