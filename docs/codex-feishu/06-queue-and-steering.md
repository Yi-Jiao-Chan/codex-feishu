# 06 默认排队与显式追加引导

负责 `internal/submissions/`。依赖 01、02 及 03 的归一化输入，输出 00 定义的状态数据，由 08 呈现；组合根把按钮路由到本模块，不反向导入 cards。这是一期并发正确性的主要模块。

## 普通输入

所有普通飞书输入都走同一流程：校验 sender/绑定 → ClaimInbound → 保存收据和稳定 clientUserMessageId → 必要时恢复原工作树 → `thread/queue/add`。不先判断空闲再调用 turn/start；否则 App 可能同时启动，普通输入会误变成引导。

符合[单人任务群条件](03-feishu-gateway.md)的免 @ 文字/富文本也走这条路径；仍按消息 ID 去重，空闲继续原会话、忙时排队，不自动 steer。

queue/add 的本地验证行为是空闲自动执行、忙时排队。成功响应后刷新 queue/list 与用户历史，以事实更新“已排队 / 已执行”，不假定返回的项一定还在队列。

已绑定会话的托管工作树被回收时，普通消息先落库，再从原路径对应的 Codex 快照恢复，然后附着原线程并提交原收据。原 cwd 是子目录时保留相对位置。恢复进度、快照缺失或结果未知更新引用原消息的管理卡，消息保持待提交且可按原规则本地取消；不会只停留在 GET reaction。升级前已收到、确认从未提交的普通消息也可触发恢复；没有新输入或待处理收据时，历史同步不主动恢复目录。没有快照、身份冲突或未决原生写入时保留消息，不从当前分支重建或盲重发。范围与限制见[工作树恢复](09-feishu-task-creation.md#已回收工作树的消息恢复)。

在领取原生写入 attempt 前还会只读复查当前 cwd，避免 actor 检查后到提交前的目录回收把本地待提交输入变成 unknown。发现缺失时保留原收据并唤醒恢复；这不锁住 App，真正 RPC 期间发生的外部清理或响应丢失仍按原生 unknown 规则核验。

停止后主动发送新的普通消息，也表示继续处理同一会话，不要求另发 `/continue`。接收入口在新消息首次入账的事务内保存继续意图，只有本地已观察到中断或已有明确的停止意图时才建立；新输入仍先 `queue/add`，确认接收后经原 actor 核验目标轮及队列，再调用 `queue/start`。没有新消息时，停止前的队列继续保留。重放旧消息、附件下载完成、重启或补历史不生成新的继续意图；后到的停止覆盖此前继续意图，未决写入先核验，不越过 unknown 自动恢复。队列顺序仍以原生 FIFO 为准，不把新输入改成 steer。

异步问题卡的“提交回答并追加”是显式引导操作：回调原子保存完整答案、原生输入收据与初始 steer 动作；有活跃轮时直接 `turn/steer`，不先 queue/add 或 queue/delete。目标轮在发出前冻结，重连和轮次切换不改投另一轮。空闲或 steer 明确拒绝时，沿用可靠的 queue/add 继续会话；此时遵守普通收据 FIFO，不越过较早的 collecting 附件。活跃轮的显式追加与现有引导一样可以越过普通排队输入。显式停止的原生队列继续保留，不隐式 queue/start。结果 unknown 先核验原目标轮的 clientId，不重发或改用 queue/add。

回答状态和操作始终更新原问题卡。旧卡片没有明确追加标记的回调、升级前已保存的答案和已存在的排队项保持原来的排队行为；不会因重启自动升级成 steer。原有“追加引导 / 移除”仍校验真实卡片消息 ID、收据 token、原生队列 ID 与 revision；独立排队投递保持原有归属，unknown 不迁移。

收据与原生执行队列分开：SQLite 保存操作和核验状态，执行顺序以 Codex 原生 queue 为准。queue/changed 到来后分页读完整队列，显示真实序号，不能把“当前桥第几条”当整体队列位置。

## 多段原生输入与收取顺序

附件封存后，submission 同时保存显示正文和冻结的 `input_json`。图片是安全缓存文件的 `localImage`，通用文件是包含名称和绝对路径的文本引用；完整数组原样用于 queue/add、steer 和 restore，不能在 steer 或 restore 时退化成正文。普通旧收据没有 `input_json` 时继续走原来的 Text API。

sealed 但仍下载中的输入保持 `collecting`，同一线程后来的普通提交在 FIFO 迭代处停止，避免文字越过它；整批 ready 后才发原生写入，整批 failed 后释放后续提交。明确失败的本地下载可重新入队到队尾并保留 client ID，已经有 native attempt 的收据不能这样重发；unknown 只核验 queue/history，不再次发送。控制动作和停止仍可处理，不被 collecting 的普通输入阻塞。

队列恢复优先使用只含 ID/client ID 的 `thread/queue/list` metadata DTO，避免把 canonical image data URL 写入本地快照；完整输入只在真正需要提交或历史语义核验时读取。单批最多 10 个资源、5 张图片；单图 10 MiB、图片合计 20 MiB、普通文件 20 MiB、批次 50 MiB，单图像素 40M，原生请求预算 32 MiB。

带说明、自动封存且没有既存草稿卡的附件输入，收取与正常进入会话只用 reaction 反馈；实际排队、核验、提交或下载失败、断线待提交时才创建操作卡。需要手动发送的附件草稿仍保留管理卡，整批收齐后复用为 QueueView，不另发附件摘要；明确的本地下载失败保留重试入口。已投递卡的真实 ID 和原引用保持稳定，按钮仍核验收据、原生队列 ID 和版本。断线时禁用原生操作，只有证明从未提交的输入可本地取消。

## 追加引导算法

只允许有效队列项和可用活跃轮；状态过期时返回刷新提示。每个 ThreadKey 使用本桥 actor，但不能认为它锁住 App。

```text
1. 领取 action token，核验操作者 / 卡片版本 / binding / 原生 queue ID。
2. 从最近可信的原生状态取得 active_turn_id；持久保存 steer intent。
3. queue/delete(queuedSubmissionId)。
   deleted=false：停止；核验已执行、已删除或其他变化，不再 steer。
   unknown：进入 reconciling，不进入第 4 步。
   deleted=true：持久保存删除成功，进入第 4 步。
4. turn/steer(expectedTurnId=步骤 2 的 turn，原内容和相关 ID)。
   confirmed：保存响应；再用事件/历史关联真实 user item。
   rejected 且明确未接受：按第 5 步恢复。
   unknown：核验目标 turn 的 userMessage.clientId，禁止重发。
5. 明确未接受且内容不在队列/历史：重新 queue/add 保留原相关 ID。
   记录新 native queue ID；提示可能移到末尾。
```

步骤 2 后 App 开始另一轮时，expectedTurnId 必须仍为原值；不能在失败后偷偷换成新轮 ID 再 steer。当前轮已结束的明确拒绝按后续排队输入恢复；空闲时 queue/add 可以自然启动下一轮。

delete + steer 是两个 RPC，没有事务保证。删除成功保存前崩溃、App 同时消费、App 同时引导和轮次结束都必须交给 02 的 attempt journal 核验。**队列项消失本身不是 steer 成功证据。**

原生 clientUserMessageId 只是关联字段。桥同一收据最多一个未完成提交尝试；重复卡片事件读取原动作结果，不能因为相关 ID 一样就安全再发一次。

受控验收的专属绑定使用 Controller.BeginWrite：每个原生写阶段在领取 attempt 前单独检查，操作上下文贯穿该次 RPC 与结果保存。删除成功不使下一次 steer / restore 自动获授权，拒绝或取消不新发输入；nil hook 保持普通路径。完整受控 CLI 编排和真实双客户端重验仍 pending，见[操作授权进展](../records/m3-verification-operation-guards-2026-10-12.md)。

## 允许的卡片状态

| 后端事实 | 卡片文案 / 操作 |
| --- | --- |
| 尚未提交 | 已收到，正在提交；不能显示已排队 |
| 原生队列仍有项 | 已排队 · 第 N 条；执行状态以原生队列为准 |
| 已验证停止 / interrupted | 队列已保留；发送新消息或显式继续可恢复，没有追加引导按钮 |
| 离线且确认从未提交 | 待提交；可在引用原消息的卡片取消本地待提交项 |
| 工作树已回收且尚未提交 | 原消息已保存；同一回复卡显示恢复进度或具体阻塞，可取消本地消息 |
| 领取引导动作 | 正在追加引导；禁用同项冲突操作 |
| 引导确认 | 已追加至当前轮 |
| 明确拒绝并恢复成功 | 当前轮已变化，已保留为后续消息；位置可能变化 |
| 已被原生消费 | 已执行；显示实际轮次，不再追加 |
| 接收结果未知 | 正在核验是否已接收；禁用重试/追加 |
| 移除确认 | 已移除；不再次提交 |

App 端原生排队消息可以展示队列位置。首版只给桥有完整内容和收据的项提供引导/移除按钮；若要操作 App 排队项，先补齐其持久收据、原生 ID 和同样的并发验收，不能仅凭卡片摘要执行。

## 移除、停止和恢复

移除调用 queue/delete：true 更新已移除，false 核验已消费/已移除，不给出假成功。处于引导/核验中的项不接受并行 remove。

停止当前轮提交真实 turn_id 的 turn/interrupt。确认后显示已停止，保留队列；停止后新收到的普通输入、“继续执行队列”或 App 自己显式执行都可以恢复。恢复调用 queue/start，仅空闲有效；遇到 busy 刷新当前轮，不改成 steer。已有 CoT 显示中断时省略额外成功回执及空正文停止结果卡，详见 [08 卡片](08-cards-and-actions.md#当前执行进度原生-cot)。

CoT `/stop` 在命令入账时冻结唯一活动轮次；已知原生终态的旧轮次不参与候选判断，即使其飞书终态追加或 Complete 仍为待处理、拒绝或 unknown，也不阻塞新轮停止。候选不唯一时仍拒绝，原 actor 发送前继续核验冻结的 turn_id，不改投后继轮次；旧 CoT 的投递日志保持原状态，不因停止新轮而标成成功。

原生停止后 add 本身仍保留暂停语义，参见 [OpenAI 原生队列测试](https://github.com/openai/codex/blob/main/codex-rs/app-server/tests/suite/v2/thread_queue.rs)。桥仅对新的主动输入保存并执行一次继续意图，不修改 daemon 策略；新入口的真实客户端行为仍需验收，不能只用“停止前已排队”或低层 add 测试替代。

断开 Codex 时可以持久接收新飞书输入并标待提交，恢复且目标仍有效后提交；用户移除待提交消息只取消本地收据。若有 unknown 尝试，不能把它当从未发送的待提交项取消并重发。

开发版已实现严格的本地取消：操作者、绑定、真实远程卡片 ID、token 和收据 revision 在同一短事务核验；必须没有任何原生提交 attempt、M0 写入日志、历史关联或未决动作。取消与 actor 领取提交竞争只有一个赢家，重复回调读取原取消结果。卡片不重复展示人类正文，结果更新同一引用卡。

离线卡片由原生代际的拥有者串行发送：旧 Runtime / actor 已全部退出，下一代 journal recovery 尚未开始。退避期间周期处理新收到的消息，反馈的 deadline 不超过下一次重连时间；不会由常驻收消息循环跨代领取 mirror。原生 Queue DTO 不含 paused 状态，因此即便有活跃轮，也不据此承诺队列自动启动；活跃轮只决定是否显示追加引导。实际 UI 仍需新版部署后集中验收。

## 验收场景

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| Q1 | 空闲输入；忙时输入 | 同一入口分别执行 / 排队，忙时不改变当前轮 |
| Q2 | 忙时连续 A/B/C，包含 App 队列项 | 原生顺序一致，序号真实，正常消费各一次 |
| Q3 | 将 B 追加引导 | B 进入目标活跃轮，原队列不再执行 B；A/C 顺序保留 |
| Q4 | App 同时删除/消费 B | deleted=false 后不再注入 |
| Q5 | 删除后轮次恰好结束 | 明确失败后恢复后续消息；不引导新轮 |
| Q6 | steer 成功但响应丢失 | 从目标 turn 历史确认，只执行一次 |
| Q7 | queue/add 成功但响应丢失 | 队列/历史找回，不二次 add |
| Q8 | delete 响应丢失、阶段间崩溃 | 核验或明确阻塞，没有盲目 steer |
| Q9 | 同按钮重放、多名操作者并发 | 同一动作只执行一次；旧版本拒绝 |
| Q10 | 停止、新消息恢复、显式恢复、同时 App 启动 | 没有新意图时保留队列；新消息确认入队后恢复；后到停止优先；busy 不误引导 |

Q4–Q10 要在双客户端及故障注入下验证。仅用本桥 mutex 的单元测试不能证明这些并发行为。
