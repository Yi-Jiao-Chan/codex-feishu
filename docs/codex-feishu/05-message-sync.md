# 05 双向消息同步

负责 `internal/sync/`。依赖 01–04、07 的通知决策和 08 的渲染接口；飞书到 Codex 的实际输入写入由 06 负责。

## 可见内容与来源

必需镜像：所有人类 userMessage、公开 agentMessage（含公开进度与最终回答）。计划和工具状态可作为任务卡的折叠摘要。reasoning item、内部 function output、全量命令日志不直接当 AI 对话发布；需要的公开执行结果从公开回复和摘要表达。

统一页脚：

```text
人类发送 · Codex 端 · 16:20
人类发送 · 飞书 · 张三 · 16:21
AI 回复 · Codex · 16:22
```

只有可靠来源字段时才进一步写 App/CLI。Codex 端原生输入没有可核验人名时不冒充 owner；飞书发送者从消息 open_id 与该事件的身份信息关联。

## 镜像流程

1. 事件定位 ThreadKey 与绑定/创建意图；已决定自动绑定但暂未建群的线程继续保存公开事件和待绑定投递，绑定后补齐历史。
2. item upsert 到镜像状态，转换成 MirrorDocument；持久 outbox 后再推进同步水位。
3. 第一次可见正文发卡并保存 message/card ID；公开增量合并到同一卡，目标最短更新间隔 800ms，仍服从平台限流。
4. item completed 用完整正文纠正增量丢失；最终状态不能被迟到 delta 覆盖。
5. turn completed / failed / needs-user 更新任务卡，按 07 判断是否发送简短 @ 通知。

镜像键使用 `(host, thread, item, segment_index)`。长正文超过平台实际限制时按代码块与段落边界拆成稳定分片，标明第 N / 共 M 段；不能静默截断最终回答。M0 记录当前 Card/API 大小和元素限制后确定阈值，不凭经验写死“飞书一定支持任意长内容”。

## 飞书输入的回显与去重

输入收到后，06 建收据并发排队状态卡。历史 userMessage.clientId 匹配该收据时更新这张状态卡为已执行/已引导，并保存原生 item/turn；不再新发一份同样的人类镜像。

Codex 端原生输入没有桥收据，正常生成独立人类镜像。App 原生队列项也可由 queue/list 显示位置；采用原生 queue ID 稳定关联，消费后和 user item 合并。桥接收的飞书镜像事件不会变成第二次 Codex 输入。

App 实际可见性的验收分两步：忙时输入出现在 App 队列；执行或引导后出现在同一线程的聊天记录。读取 rollout 正确不能代替 App 页面实测。

## 初次绑定与断线补齐

自动新绑定补从首条输入开始的全部公开内容；显式绑定历史线程默认补最近一轮。重连与历史绑定的补齐标记 `replay=true`，只补内容，不新安排 @。已持久安排的新事件通知由 outbox 按 07 的规则继续或抑制。

新任务的首次自动绑定区别于旧历史绑定：创建意图已确认它是基线后的新任务，即使首轮在建群前完成，也可按真实 turn.completedAt（0.162.0 中以 Unix 秒表示）和当前策略安排一次最终通知；两次判断都允许才 @。时间缺失或不能确认是新任务时只同步正文，不补提醒。这样快速完成的新任务可以提醒，而休息期间完成的结果不会早上补 @。

补齐先读元数据，然后分页 turns/items，依持久水位与重叠窗口 upsert。生成中 item 重新读取最新完整状态再订阅增量；既不能只重放 delta，也不能简单在重连时将整个线程全文再发一遍。

话题绑定的所有分片、来源页脚和通知均沿用 topic target。没有有效话题时保持待投递状态，由 03 处理，不发主群。

## 故障反馈

Codex 断开：任务卡显示最近已知状态及时间，禁用实时引导/停止。飞书断开：原生任务继续，公开最终内容进入 outbox，恢复后补齐。待审批或问答：显示“请回 Codex App 处理”，不以普通群消息作为原生回答。

## 验收

1. App 首条人类输入、公开进度、最终回复按顺序到群，来源可辨。
2. 飞书输入执行后更新原输入卡；人类镜像、机器人事件均不形成循环。
3. delta 丢失、重复、乱序和完成后晚到，最终正文仍与完整 item 一致。
4. 长代码/中文正文稳定拆片；重连更新原分片，不重复全文。
5. 不公开 reasoning；回 App 审批不改变原权限。
6. 断线跨多轮、重启后正确补齐，旧历史没有批量 @。
