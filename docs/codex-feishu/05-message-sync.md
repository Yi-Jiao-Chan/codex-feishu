# 05 双向消息同步

负责 `internal/sync/`。依赖 01–04、07 的通知决策和 08 的渲染接口；飞书到 Codex 的实际输入写入由 06 负责。

当前实现：`cards.SplitMessage` 按完整 JSON 字节上限拆分正文，保留原始字节，代码块分片补齐匹配的围栏与语言；`sync.Engine` 将完整原生历史转换成公开镜像，关联飞书 clientId 收据，保持每轮首条输入锚点；`sync.Outbound` 投递持久镜像并更新原卡。schema v4 的镜像 / outbox / 输入关联 / 水位在同一事务保存，真实回复父消息在领取投递时解析。已通过真实 daemon 0.162.0 的只读历史探针；正式 serve 的通知、队列 / reaction、多线程组合已有开发实现及隔离测试，正式部署与 UI 验收仍待完成，现有 M0 仍使用独立测试实现。长代码的分片本地测试不能代替正式链路的飞书客户端验收。

正文使用多个 native Markdown 块后，旧的单字段字节估算仅用于寻找候选范围；候选和段落/行边界都通过实际 renderer 校验。完整卡片、段数来源、围栏补齐和提醒/标记预留仍严格遵守字节上限，附件合卡也单独实际验收；原始 Raw 和原生历史不因显示间距或引用样式变化而改写。

## 可见内容与来源

必需镜像：Codex 端原生人类 userMessage、公开 agentMessage（公开进度聚合到过程卡，最终回答单独发送；飞书人类输入不在群内重复镜像）。计划和工具状态可作为任务卡的折叠摘要。reasoning item、内部 function output、全量命令日志不直接当 AI 对话发布；需要的公开执行结果从公开回复和摘要表达。

公开 assistant 回复中的 App `visualize` 包装在聚合与卡片分片前转换，仅改变展示副本。预览开启且 HTML 文件位于显式授权范围内时，显示「查看可视化 · 静态预览」及交互版回 Codex 的提示；正文已有同一文件的可用预览链接时复用该入口，多次嵌入同一文件也只保留一个入口。预览关闭、文件失效、超限或无权访问时，显示「请回 Codex 查看可视化。」；边界可确认的已知畸形包装也使用该提示，已消费的包装不直接展示内部 JSON 与路径。代码围栏、缩进代码、行内代码及反斜杠转义的示例保持原样，未知种类的标记不猜测转换。生成中未闭合或跨行损坏的包装只消费当前行或下一个标记之前的内容，遇到代码则提前停止，不猜测后续正文的归属；完整且结构合法的多行 JSON 包装可以整体转换。完整快照到达后重新投影。预览登记失败仍按下方规则停止本轮快照，不推进水位。

展示转换在关闭预览和旧历史恢复时同样生效。已有最终卡片沿原镜像键增加版本并更新原消息，不重复发送或补发提醒；未知投递继续先核验。部署更新后须等待对应会话的历史协调，代码与本地回归不代表已发卡片已经完成真实修正。原生历史、用户输入和文件本身均不改写，预览目录与静态 HTML 的边界见 [14 网页预览](14-file-preview.md)。

2026-10-13 附件输入展示：仅识别完整、已知的 App 附件包装，正文显示实际 My request 内容，图片与文件引用分开展示；未知包装原样保留，原生 PublicText 不变。已确认上传的图片以小缩略图附在人类卡内，点击查看原图；随机文件名、完整本地路径与文件清单置于折叠详情，不把本地路径伪装成下载链接。App 历史附件包装中的通用文件仍是清单展示；飞书入站资源按下方流程进入受限本地缓存。只有 native 图片引用或已验证附件物理目录中的文件可读；不抓取正文中的远程图片 URL，非图片/超限制/响应未知保留正文及简短占位。上传发送前持久记账，同一应用相同图片复用已确认 key；未确认上传不盲重试。截图文件 wrapper 与原生 image 的重复表示按内容配对，保留附件名而不重复展示图片。

2026-10-15 异步问答回答展示：完整的 `send_user_message_question_reply` 包装经题目身份、字段和答案校验后，按原顺序显示加粗问题和回答正文，不额外添加“问题／回答”标签或公开内部 call ID 与 JSON 包装。转换独立于异步问题卡开关，原生 PublicText 与输入收据不变；飞书发起的回答仍按 clientId 收据去重，重连复用原镜像，已发送的旧格式卡片通过原消息更新。启用交互扩展后，异步提问始终生成独立问题卡；未允许飞书填写时提示回 App，首次按 needs_user 策略提醒，App 回答后原卡显示已核实的答案。引用示例、未知字段、重复身份或不完整包装保留原文。多题、长回答拆片和本地恢复已有回归，真实客户端展示仍待验收。

## 飞书图片、文件与多附件输入

入站静态 PNG/JPEG/WebP 按消息顺序保存为受限本地资源，原生输入使用 `localImage`；通用文件以带文件名和绝对路径的文本引用交给同一远程会话，不做 OCR、解压或自动执行。按 2026-10-15 用户实测反馈，图片只保留用户原文和图片，不再插入附件说明；文件只追加转义后的 `"名称": "绝对路径"`，原生协议没有通用 file part，因此路径仍是工具读取文件的必要信息。无说明而点击发送时仅使用“请查看附件。”作为默认输入。`attachments.enabled=true` 时，单条 `/new` post 可同时带正文、图片和顶层 `files`；私聊及已授权未绑定入口群的普通图文/文件说明沿现有创建入口建草稿，已绑定群/话题的普通输入继续现有会话，只有 `/new` 建草稿。群 post 必须结构化 @；独立图片/文件仍仅在已绑定任务群按 `receive_standalone` 接收，不扩展私聊或未绑定入口群的独立附件收集。真实 App 的视觉识别、文件工具读取和手机显示仍需人工验收。

附件草稿按 `(host, app, thread, chat, sender)` 隔离。创建草稿持久保存不可编辑的有序资源描述（来源 `key`、`name`、`kind`），正文仍可在原创建卡编辑并显示附件计数；`/new` 只带附件时预填“请查看附件。”。连续资源先更新同一张草稿卡；带说明的提交在封存时原子成批，卡片发送也使用同一封存路径。所有资源 ready 后才冻结完整 `input_json`，queue/add、steer 和 restore 都使用同一数组；附件不在飞书再次镜像正文。管理命令不消费草稿，关闭开关也不取消已封存批次；未确认草稿带附件提交会提示重新开启。

统一页脚：

```text
人类发送 · Codex 端 · 16:20
人类发送 · 飞书 · 张三 · 16:21
AI 回复 · Codex · 16:22
```

只有可靠来源字段时才进一步写 App/CLI。Codex 端原生输入没有可核验人名时不冒充 owner；飞书发送者从消息 open_id 与该事件的身份信息关联。

## 镜像流程

可选 `file_preview` 启用后，公开 assistant 文本中的本地文件链接在卡片拆片前转换为受鉴权保护的网页地址，保留行号；文件映射先本地持久化，再进入既有 outbox。转换使用独立展示副本，不改变原生历史或用户输入，`cards` 保持纯渲染。登记失败不推进本轮快照，错误正文不进入诊断。详见 [14 网页预览](14-file-preview.md)。

1. 事件定位 ThreadKey 与绑定/创建意图；已决定自动绑定但暂未建群的线程继续保存公开事件和待绑定投递，绑定后补齐历史。
2. item upsert 到镜像状态，转换成 MirrorDocument；持久 outbox 后再推进同步水位。
3. **按 turn 聚合过程，不按 agentMessage 逐条发消息。** 每轮最多创建一张过程卡，保存 message ID；公开 commentary / partial_answer 更新原卡，合并窗口内变化，最短更新间隔 2 秒。正文只保留最新公开动作摘要；工具仅显示状态摘要，不转发 reasoning / 全量命令输出。
4. item completed / 原生完整快照纠正公开增量。相同卡片内容不 PATCH；所有发送和更新由线程 actor 串行处理；完成后不接受迟到进度覆盖。
5. turn 终结将过程卡压缩成完成 / 失败 / 停止状态。按原生 phase=final_answer 聚合最终正文，**另发一张最终结果卡**；无 phase 的历史模型兼容最后一条公开 agentMessage，不把明确 commentary 当最终答案。正文过长才分片。
6. 最终结果投递成功后，原飞书输入的 reaction 转为完成；按 07 决定是否 @。过程卡不 @，原消息 reaction 不代替最终结果提醒。

异步提问也可能携带 `phase=final_answer`。同轮后续出现普通最终答复或无 phase 的历史答复时，展示聚合排除它之前 `delivery=async` 且带 questions 的提问，不依赖交互开关、服务启动时间或问题记录是否存在。没有后续答复的旧问题继续可见，不把提问前的过程前言误认为答案；已有最终卡按原消息更新，原生历史不改写。

过程键使用 `(host, thread, turn)`；最终投递键使用 `(host, thread, turn, segment_index)`。内部仍按 item ID 合并公开文本以去重。长正文超过平台实际限制时按代码块与段落边界拆成稳定分片，标明第 N / 共 M 段；不能静默截断最终回答。阈值同时检查序列化 JSON 的字节大小；M0 当前短文本验证不等于长代码分片已经验收。

完整终态正文被纠正、分片数减少时，未发出过的尾片在本地取消展示；已确认存在的尾片 PATCH 成小段合并提示，避免旧正文残留。未知投递的尾片仍须核验，不通过重新发送清理。生成中的最新动作摘要可以缩短以适配卡片字节上限；人类正文与最终回复完整拆片。

## 回复关系

机器人过程卡与最终结果使用真实消息回复接口引用该 turn 的第一条人类输入。飞书发起的轮次引用原 message_id；App 发起的轮次引用已发送到群的人类镜像卡。队列 / 引导操作卡引用对应补充输入的原 message_id；引导不会改变原过程卡的引用目标。

普通群跟进明确 reply_in_thread=false，不主动创建新话题。保存父消息与回复 message_id，后续 PATCH 不改变关系。父消息未投递、被撤回、不可回复或响应未知时核验 / 记录失败，不静默退化为无关联普通消息。二期 topic 仍使用其明确目标参数。

## 飞书输入的回显与去重

飞书原消息就是群内人类上下文，机器人**不重复发布正文**。收到后保存收据，在原消息上添加 reaction。只有确认仍在原生队列的输入才发紧凑操作卡：状态 + 横排“追加引导 / 移除”，不带输入摘要和人类来源页脚。空闲输入被原生消费时不另发“已进入会话”收据卡；已有队列操作卡更新状态。

历史 userMessage.clientId 匹配桥收据时保存原生 item / turn 关联，更新原消息 reaction 与已有操作卡，不再发送同样的人类镜像。Codex 端原生输入没有桥收据，正常生成独立人类镜像；不伪造作者身份。App 原生队列项以 native queue ID 关联；桥事件不会形成第二次输入。

App 可见性验收分两步：忙时出现在 App 原生队列；执行或引导后出现在同一线程记录。读取 rollout 正确不能代替 App 页面实测。

原消息 reaction 状态采用飞书官方 emoji_type：Get=接收，OneSecond（稍等）=排队，THINKING=附件收取中或等待用户处理，OnIt=执行，CheckMark=完成且最终结果已投递，CrossMark=失败；移除 / 停止清理本机器人临时状态。不删除其他人的 reaction。reaction 缺权限或请求结果未知只影响反馈，不能造成 Codex 输入重试；未知响应不盲重试。

受控验收绑定的卡片、reaction、命令确认和提醒已接入逐次发送授权与资源上下文，领取前拒绝不会生成 attempt，领取后取消保持保守恢复。reaction 的已确认删除与尚未 journal 的添加可凭本地证据继续，不能重复删除或据远程缺失猜测重试。管理绑定入口已接入；真实服务部署与 UI 重验仍 pending，见[投递上下文进展](../records/m3-verification-delivery-guards-2026-10-12.md)和[管理绑定组件](../records/m3-managed-binding-2026-10-12.md)。

## 初次绑定与断线补齐

自动新绑定补从首条输入开始的全部公开内容；显式绑定历史线程默认补最近一轮。重连与历史绑定的补齐标记 `replay=true`，只补内容，不新安排 @。已持久安排的新事件通知由 outbox 按 07 的规则继续或抑制。

新任务的首次自动绑定区别于旧历史绑定：创建意图已确认它是基线后的新任务，即使首轮在建群前完成，也可按真实 turn.completedAt（0.162.0 中以 Unix 秒表示）和当前策略安排一次最终通知；两次判断都允许才 @。时间缺失或不能确认是新任务时只同步正文，不补提醒。这样快速完成的新任务可以提醒，而休息期间完成的结果不会早上补 @。

补齐先读元数据，然后分页 turns/items，依持久水位与重叠窗口 upsert。生成中 item 重新读取最新完整状态再订阅增量；既不能只重放 delta，也不能简单在重连时将整个线程全文再发一遍。

话题绑定的所有分片、来源页脚和通知均沿用 topic target。没有有效话题时保持待投递状态，由 03 处理，不发主群。

## 故障反馈

已绑定会话在成功读取元数据和历史、距最后活动超过 24 小时、运行状态为 idle/notLoaded 且轮次均终态后降低频率：原生元数据/历史约每 5 分钟补偿，本地投递、unknown 只读核验、reaction 和提醒约每 15 秒继续协调。状态或时间未知、未完成轮次、未知原生写入及当前重试错误保留普通频率。原生事件、飞书输入或置顶集合变化会立即唤醒冷 actor，先重新读取并授权元数据，再处理工作；活跃会话仍保持原先约 15 秒历史补偿和事件驱动同步。降频不改变既有确认/unknown 规则或非幂等重发边界。

Codex 断开：任务卡显示最近已知状态及时间，禁用实时引导/停止。飞书断开：原生任务继续，公开最终内容进入 outbox，恢复后补齐。待审批或问答：按 [13 审批与问答](13-feishu-approvals-and-questions.md) 显示操作卡；同步与异步问答默认可提交，未启用类型或敏感请求提示回 App。普通群消息继续走输入队列，不能代替同步问答的原生 callback 回复。

## 验收

1. App 首条人类输入到群，公开进度同轮同卡更新，最终回复单独发送，来源可辨。
2. 飞书输入不被机器人重复展示；原消息 reaction、队列操作卡按实际状态更新；机器人事件不形成循环。
3. delta 丢失、重复、乱序和完成后晚到，最终正文仍与完整 item 一致。
4. 长代码/中文正文稳定拆片；重连更新原分片，不重复全文。
5. 不公开 reasoning；回 App 审批不改变原权限。
6. 断线跨多轮、重启后正确补齐，旧历史没有批量 @。

受控绑定的实际 Service.Run / 原接收器 / actor / 管理 socket 隔离整合测试已覆盖：同一 owner 输入重放只 add 一次；进度更新原卡，最终结果独立引用原输入；最终发送确认之前没有完成 reaction；所有 reaction 指向原消息；飞书输入、reasoning、完整工具输出不镜像。原生与飞书网关均为测试替身，这份证据不提升真实 UI 或完整 P1，见[正式消息闭环](../records/m3-managed-roundtrip-2026-10-12.md)。
