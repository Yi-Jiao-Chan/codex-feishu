# 飞书目录选择：交互模式对标与方案判断

研究日期：2026-10-15。范围仅为目录选择的 UI/UX，不修改生产代码。本轮回答用户提出的四个问题：不知道哪里能点、异步操作没有完成感、少量目录也反复翻页、底部搜索后还要去顶部确认。开源项目的全量调查沿用[已有研究](feishu-create-directory-ux-research-2026-10-15.md)，这里只复用最贴近的 HAPI 与 agents-to-im。

**优先建议：一个紧凑的“查找并选择目录”视图，默认呈现已知候选，显式提交搜索，结果旁直接“使用”；逐层浏览是该视图的次模式。**“使用”只保存目录选择并返回创建摘要，最后的“开始任务”仍在主创建卡。不要把已知项目、完整目录树、路径输入和两处确认纵向堆成一张长卡。

这是设计判断，不是已经完成可用性测试的结论。下文中的 picker 指逻辑上的选择视图，可以由原消息卡更新实现；不声称飞书存在 VS Code 式弹层、固定工具栏、自动聚焦、每键搜索或可控制的滚动位置。平台组件能力由本轮另一份官方核验承担。

## 一手来源给出的模式

| 已验证的事实 | 对本项目有用的部分 | 不能直接照搬的部分 |
| --- | --- | --- |
| VS Code 将 Explorer 的探索导航与 Quick Open 按名称定位区分；其最近文件夹/工作区由独立 Quick Pick 呈现。[代码导航](https://code.visualstudio.com/docs/editing/editingevolved#_quick-file-navigation)、[最近文件夹/工作区](https://code.visualstudio.com/docs/editing/getting-started/tips-and-tricks#_navigate-between-recently-opened-folders-and-workspaces) | 为“知道目标”提供短路径，不要求每次都从目录树找起 | Quick Open 主要是工作区文件导航，不能当作任意远程目录搜索能力的证据；键盘快捷键与即时过滤也不是飞书卡能力 |
| VS Code Quick Pick 可用主标签、description、简短 detail 和分组表达候选；官方不建议把它做成长 wizard。[Quick Picks UX](https://code.visualstudio.com/api/ux-guidelines/quick-picks) | 主行识别项目，次行区分路径；只做一次目录选择，不再串联“选中—顶部确认—返回” | 不由此推导飞书支持相同字段、快捷键、弹层或多步控件 |
| Apple HIG 建议搜索占位提示说明可搜索内容、可在搜索开始前给建议，并优先呈现相关结果。[Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields?changes=_1) | 写清“搜索已知项目或粘贴绝对路径”；空输入也给合法候选 | HIG 的“条件允许时输入即搜”不是本平台必须或已经具备的能力 |
| Fluent 将长列表可输入过滤交给 combobox；普通单选选中后关闭列表、显示选中值，placeholder 不能替代字段标签。[Combobox](https://fluent2.microsoft.design/components/web/react/core/combobox/usage) | 搜索、候选、当前选择是一个连贯任务；已选值应留在主表单上可见 | 自由文本不等于有效目录，输入内容必须经远程校验；不能把 Fluent React 控件当飞书组件 |
| Fluent 按钮文案应描述下一步动作；同一布局只突出最重要的一个动作。状态应同时用文字表达，不能只改图标/颜色。[Button](https://fluent2.microsoft.design/components/web/react/core/button/usage) | 用“进入”“使用此目录”“开始任务”区分导航、目录选择与真正创建 | 不要求每一行都是醒目的主按钮，也不靠整排彩色按钮制造可点击性 |
| Fluent 的局部加载应留在加载区，不阻塞其他部分；进度说明尽量对应触发动作。[Spinner](https://fluent2.microsoft.design/components/web/react/core/spinner/usage) | 正在搜什么、正在打开哪里、成功到了哪里应在同一区域连续呈现 | 飞书是否有可用原生 spinner/按钮加载态需核验；没有时使用准确文字，不能虚构动画或百分比 |
| Microsoft BreadcrumbBar 用于显示层级位置和返回祖先；当前项通常不再次导航。[BreadcrumbBar](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/breadcrumbbar) | 浏览模式始终显示当前位置；提供上一级，深层路径可返回祖先 | 横向面包屑可能在手机上挤占空间；不强行照搬桌面全路径横排组件 |

与本项目最接近的实现证据：

- **HAPI：选择与创建分离。**最近路径/建议点击只 `setDirectory`；单独 Create 执行创建。远程目录面板的 Start Session 也只是带机器、目录返回新建表单。[选中逻辑，固定提交](https://github.com/tiann/hapi/blob/5847b034e5cb84f2617766945c994b7905c5c03e/web/src/components/NewSession/index.tsx#L1474-L1486)、[浏览返回新建表单](https://github.com/tiann/hapi/blob/5847b034e5cb84f2617766945c994b7905c5c03e/web/src/router.tsx#L990-L1006)。**本项目建议：**目录“使用”完成后回到主创建摘要，不再要求目录视图内第二次确认。
- **agents-to-im：飞书同卡选值后提交已有源码先例。**工作区单选与模式提交按钮位于同一 form；提交处理器读取 `form_value` 再创建。[表单](https://github.com/francize/agents-to-im/blob/92394e478801d872ada6f85d8f08bd38553946b6/src/feishu/cards/session-cards.ts#L174-L216)、[提交处理](https://github.com/francize/agents-to-im/blob/92394e478801d872ada6f85d8f08bd38553946b6/src/feishu/handlers/session-handler.ts#L75-L99)。**本项目建议：**主卡上保留明确的已选目录与最终创建动作；这份源码不证明卡片支持远程实时筛选。

## 四个问题对应的设计决定

表中“改法”和“验收”均为本项目建议，不是外部产品事实。

| 用户问题 | 改法 | 可观察的验收结果 | 依据 |
| --- | --- | --- | --- |
| 不知道按钮可点 | 使用真实按钮/单选控件；按钮写动作，不把普通目录文字、emoji 或折叠箭头作为唯一入口。搜索结果用“使用”，浏览列表用“进入”；只读目录写“仅可浏览”，保留进入动作 | 首次使用者能指出如何选目录、如何看子目录；不需说明“这行其实能点”。仅靠悬停才能发现的操作不算通过 | [Fluent Button：动作文案、层级与状态](https://fluent2.microsoft.design/components/web/react/core/button/usage) |
| 点击后无完成感，反复点 | 操作区域依次呈现“正在搜索 codex…”→“已找到匹配目录”或“未找到匹配”；进入时呈现“正在打开 tools…”→新当前位置；使用后主卡持久显示“已选目录”。toast 仅补充受理/错误，不能作为唯一完成证据 | 请求变慢、失败、结果为空时都能判断正在做什么；重点击不会出现重复选择流程或误建任务。已受理不能被写成“已选择成功” | [Fluent Spinner：局部加载与具体动作说明](https://fluent2.microsoft.design/components/web/react/core/spinner/usage) |
| 目录少却频繁翻页 | 少量候选一次呈现，不为了固定的小页数制造翻页；密度通过删重复说明、缩短行高改善。多项时先提供明确范围的筛选，分页作为兜底；没有下一页时不显示可点的“下一页” | 少量目录不需要翻页即可看完；过滤作用于整个当前层/候选集，不能只过滤已加载的一页；不使用“全部目录”文案掩盖结果截断 | [VS Code Quick Pick：候选上下文与分组](https://code.visualstudio.com/api/ux-guidelines/quick-picks)、[Fluent Combobox：长列表过滤](https://fluent2.microsoft.design/components/web/react/core/combobox/usage) |
| 底部搜索完要滚到顶部确认 | 搜索框放结果前；结果行旁的“使用”就完成目录草稿选择并返回主摘要。浏览模式的“使用此目录”紧贴当前位置。取消远处的第二个目录确认按钮 | 发起搜索、看到反馈、选择结果在一个紧凑操作区完成；不依赖卡片自动滚回顶部或悬浮按钮。回主卡后已选路径与“开始任务”之间没有大段内容隔开 | [Fluent 选中值留在字段](https://fluent2.microsoft.design/components/web/react/core/combobox/usage)、[HAPI 选值与创建分离](https://github.com/tiann/hapi/blob/5847b034e5cb84f2617766945c994b7905c5c03e/web/src/components/NewSession/index.tsx#L1474-L1486) |

“反馈就近”在这里是完整状态链，而不只是把提示移近一点：用户发起动作的位置、等待说明和最终结果应属于同一逻辑区域。若平台无法在回调时立即更新加载态，必须如实区分快速受理提示与随后完成的卡片内容，不能在静态 demo 中演示不存在的客户端即时行为。

## 两个可比较的架构

### 方案一：查找优先的单一选择视图，推荐

```text
选择工作目录 · remote-dev
搜索范围：已知项目/常用目录；也可粘贴绝对路径
[项目名或 /绝对路径                    ] [查找]

codex-feishu              Codex 项目
/data/home/demo/ai-tools/codex-feishu      [使用]
tools                     独立目录
/data/home/demo/tools                     [使用]

[浏览其他目录]                 [取消选择]
```

**真实触发与状态：**进入视图即显示已知候选，输入本身不发远程搜索；点“查找”才提交。新结果区带回本次查询文本和搜索范围，防止把旧结果误当成新查询完成。点“使用”后远程校验并保存一个目录，成功切回主创建摘要；不是建群、启动会话，也不再出现另一个“确认目录”。失败则留在结果旁说明原因，保留查询和原选择。

**回退：**查不到已知项目时，可粘贴绝对路径或点“浏览其他目录”。后者切换同一选择视图的浏览模式，不在原结果下继续堆一个目录浏览器；返回时恢复查询和候选。取消选择保留原来已选目录与任务正文。

**信息密度：**项目/目录名主行，父路径用于消歧；机器名在视图级显示一次。完整路径必须可查，不能为了短而把同名目录的差别截没。近期、收藏不是前提：现有项目与配置常用目录即可形成候选；真正有数据时再标“最近使用”，没有就不制造空分区。目录项“使用”保持同等中性权重，主卡“开始任务”承担最终高强调动作。

**为什么优先：**为记得项目名、复用目录、能粘贴路径的用户提供直接入口，减少日常创建必须承担的层级导航。这个判断来自上述模式对标与当前反馈，还需真实任务观察确认；不能宣称所有用户都更快。

### 方案二：浏览优先的目录列表，适合未知位置的探索

```text
浏览目录 · remote-dev
当前位置 /data/home/demo
[上一级]                       [使用此目录]

[筛选当前层名称                      ] [筛选]
ai-tools/                               [进入]
shared/  仅可浏览                       [进入]
tools/                                  [进入]

本层目录列表
[返回查找]                     [取消选择]
```

**真实触发与状态：**“进入”只打开下一级；当前路径与列表一起更新，成功后原地显示新位置。“使用此目录”只选择当前目录。只读父目录允许进入，不提供其最终选择动作；可进入下层的可写目录再使用。筛选只在明确的当前层，执行前后都显示该路径，不能暗示整机搜索。

**回退：**上一级保留层级语义；需要深层祖先跳转时再提供精简面包屑或路径前往，不让小屏幕显示一长排拥挤按钮。“返回查找”回到方案一的查询状态。读取失败保留可理解的原位置和返回动作，不能让目录突然变空而不解释。

**信息密度与代价：**每行只负责导航，避免一行两个相似按钮。选择子目录需要先进入再使用，比方案一结果行直接使用多一道动作，但导航和选择更清楚。单层目录少时完整展示；多时先筛选，分页只承担确有剩余结果的情况。不要同时在顶部和底部放相同“确认”，也不要给主卡长期附带整个目录树。

| 判断维度 | 方案一 | 方案二 |
| --- | --- | --- |
| 用户知道项目/路径 | 直接查找、使用，优先路径 | 可以路径前往，但逐层列表价值有限 |
| 用户不知道目标位置 | 需要切到浏览模式 | 当前位置与逐层探索更明确 |
| 目录很多 | 依靠范围准确的查询收敛；无匹配时解释范围 | 依靠当前层筛选；只显示本层，不递归 |
| 手机视线与滚动 | 短选择视图、行内动作；避免跨区确认 | 路径与使用相邻；深层导航仍有往返成本 |
| 飞书能力依赖 | 可用输入、显式按钮、结果更新即可；若原生下拉搜索经核实适用，可增强，但不作为前提 | 目录列表、进入/返回与更新；不依赖桌面树形控件或 sticky 布局 |

## 需要原型与实机回答的边界

以下不是增加功能的承诺，而是验收两个架构所需的场景：

1. 同一批虚构目录分别测试“已有目标项目”“完全不知道位置”“同名目录”“只读父目录中的可写子目录”。观察用户是否知道下一步，而不是让其按讲解脚本点击。
2. 在搜索、进入、使用三个动作上分别模拟较慢响应和失败；观察是否重复点击、是否误判完成。持久结果优先于短暂 toast；客户端反馈的具体载体待官方能力和实机核验。
3. 用短列表和长列表测行高与分页。服务端允许返回多少项不是 UI 必须显示多少项；不预先宣称某个行数适合所有手机。若少量项仍翻页，或完整列表把操作区推到数屏之外，均需改版。
4. 观察卡片更新后实际滚动位置。选择架构应在不假设自动滚动/聚焦的情况下仍可理解；若客户端确实让用户持续丢失位置，再讨论新增 H5 面板，不把它隐藏成当前原生卡的能力。
5. 最终保持一个含义明确的“开始任务”：选目录、浏览、搜索不会远程创建会话；未知创建结果继续展示核验状态，不能因用户着急重复点而重复创建。

本轮未重新研究 NNG 原则，也未重新罗列五个开源项目；前者由主研究统一整合，后者已有固定源码证据。本文的决策价值是把两种工作方式分开，并为四个实际抱怨给出可以观察、可以否决的设计变化。
