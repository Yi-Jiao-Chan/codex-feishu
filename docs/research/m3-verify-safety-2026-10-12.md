日期：2026-10-12。完整一期仍未发布；受控正式验收仍待整合，`verify_managed_tests=false`。本轮没有发送测试消息或 @、创建群、提交 Codex 输入、开启真实接收器、替换 M0 实例或迁移其数据库。

## 修正的实际问题

旧 verify 在检查配置之前先创建独立 native 客户端，随后无条件调用 Store.Open；即使没有测试标志，也会创建 / chmod 数据库、切换 WAL 并运行最新迁移。新版单独解析 verify 参数，非法 target、参数或缺配置时不访问网络或数据库。默认路径复用配置 doctor 的 GET、管理健康和只读快照；不创建 native 客户端、消息接收器或可写数据库。

连接、授权及历史 M0 记录不能证明当前一期服务、App UI 或配置体验已经通过。verify 列出全部 12 项 P1 场景为必需 pending，不能返回配置完成；基础失败保留具体退出码，健康但缺验收证据时退出 5。version 同时标识 `verify_readonly=true` 与 `verify_managed_tests=false`。

开发版接受 `--allow-test-thread` 作为授权输入，但实际受控流程未接入，因此不部分发送卡片或建群。已有管理实例时也保留唯一接收器，返回 managed tests pending。原来的 owner 私聊卡 / owner-only 私有群仅保留为旧 M0 准备流程：应用锁、数据库监听锁全部取得后，才核验诊断的准确配置摘要与密钥仍未变，再打开所属用户私有 0700 物理目录内、准确 schema 1 的已有私有数据库。不存在、目录可由其他用户写入、权限不符、schema 不符或身份已变时拒绝；不创建、chmod 或迁移。

请求 UUID 在 API 前持久确认；remote success、本地结果、unknown / rejected 原意图保持一次请求，不重新生成并发送。未知响应退出 5，明确拒绝退出 4；持久记录读回只代表旧 M0 准备，不将旧回调提升为当前 P1 验收。旧准备后应使用保留的历史 M0 二进制；当前开发 m0-listen 仍会迁移数据库，不能拿它直接替换旧实例。

## 验证

自动测试覆盖默认管理检查不调用可写接口、缺数据库不创建、schema 1 在监听锁持有期间的字节 / 权限 / schema 不变；非法参数不调用依赖；受控线程未接入 / 正式实例存在时不部分写入；两把锁冲突在可写打开之前被拒绝；schema 不匹配不迁移；旧准备的 owner 范围、重复调用不再发送、unknown / rejected 不重试，以及 UUID 在网关调用时已落盘。

独立检查补了两个回归：诊断或取锁期间配置 / owner / 密钥变化时，锁后拒绝发送；私有数据库放在共享可写目录时拒绝打开。准确配置快照来自 doctor 的已校验输入，凭据只在内存；错误诊断不输出变更后的凭据与 owner。部署目录与数据库的模式 / UID 都须匹配。

实际只读运行使用现有 M0 配置：[脱敏结果](m3-verify-readonly-2026-10-12.json)。daemon、机器人与必需授权检查通过；旧实例没有管理通道，正确保留 diagnostics-pending / 5，全部 P1 场景仍待验证。前后数据库均为 schema 1、0600，原 M0 进程仍在。此结果不作为真实一期 UI 验收。

## 下一项：已有通知规则的配置更新

只读调查确认不能直接移除 setup 的 policyApplyPending：计划摘要包含旧规则，政策提交后摘要会变；现有恢复只核验配置，且先于桥锁；仅政策变更还会误走配置 no-op。需要将 before / after 政策、稳定授权摘要及配置摘要纳入版本化 prepared / applied 日志，在配置锁、应用锁与 listener 锁内复用现有 revision CAS 和政策历史事务；中断后同时核验配置及数据库，禁止新计划覆盖未完成的政策事务。

serve 也须在取锁后重读配置并检查未完成事务，避免配置已替换而政策尚未提交时启动。OpenExisting 可用于准确当前 schema 的显式本地更新，但不会代替迁移。实现和故障注入测试仍待完成；现有规则更新继续 pending，不部分应用。
